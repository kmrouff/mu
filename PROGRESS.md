# Mu — Build Progress

Tracking doc for building the "Mu" presence app from the design handoff in [README.md](README.md) / [Mu.dc.html](Mu.dc.html).

## Decisions

- **Stack**: React Native + Expo (TypeScript), app lives in [`app/`](app/). One codebase for iOS/Android, Expo Go lets us share prototype builds with a few people instantly without App Store review.
- **Expo SDK 54, not 57**: SDK 57 (and 56, 55) are not yet approved on the public Expo Go app on the App Store/Play Store as of 2026-07-17 — only SDK 54 is. Scaffolding started on 57 and was downgraded to 54 specifically so `npx expo start` + scanning the QR code in the real Expo Go app works today. Revisit the SDK version once newer Expo Go builds are publicly available.
- **Animation**: `react-native-reanimated` for breathing/pulse/heartbeat/hue-drift motion; `react-native-svg` for the orbs' radial gradients (RN has no CSS `radial-gradient`/`filter` equivalent). Reanimated 4 requires `react-native-worklets` as a **direct** dependency, not just transitive — if Expo Go ever shows `[runtime not ready]: Exception in HostFunction` with `NativeWorklets` in the stack, run `npx expo-doctor` (catches this exact mismatch) and `npx expo install react-native-worklets`.
- **Haptics**: `expo-haptics` for the mutual "both" state buzz (replaces `navigator.vibrate` from the web prototype) — approximated as two quick impacts per 1.05s tick since expo-haptics has no raw vibration-pattern API.
- **Colors**: design is authored in OKLCH. Converted once to sRGB hex/rgba via a small conversion script (see `src/theme/tokens.ts` header) — same L/C/H, nearest sRGB. The login orb's hue-rotate cycle is done the same way: 13 precomputed hue-rotated stops, crossfaded at runtime.
- **Orb gradient animation**: originally tried animating `<Stop>` (react-native-svg) colors directly via Reanimated's `useAnimatedProps` — worked in the web preview (real DOM `<stop>`) but crashed on-device in Expo Go with `[Reanimated] Cannot find host instance for this component`, because `<Stop>` renders no native view (it's gradient-definition data consumed by `<RadialGradient>`, not a host component Reanimated can attach to). Fixed in `CrossfadeGradientCircle.tsx`: pre-build one static gradient per state/hue-step and crossfade between stacked `<Circle>`s by animating opacity instead (`Circle` is a real host view, safe to animate). Lesson: always sanity-check Reanimated + SVG combos on-device, not just in the web preview — some failure modes are native-only.
- **Backend (phase 2)**: Firebase Realtime Database, free tier, no formal auth (Google/Apple sign-in explicitly descoped — see phase 2 section). Decided once the actual goal became clear: let two real people test pressing each other's orb, which needs a live data channel and *some* identity, but not App Store-grade accounts. Real native Google/Apple sign-in would've forced leaving Expo Go for a custom dev client, and Apple Sign In specifically needs a paid $99/yr Apple Developer Program membership the user doesn't have — neither was worth it for "a fun little project."

## Phase 3 — Web Distribution

Goal: the easiest possible way for casual friends/family to try `mu` — a plain link, no Expo Go install, no App Store review. Decided over native distribution (EAS Build/TestFlight/Play) after discussing tiers; the app has no native-only dependency that blocks a web build (Firebase JS SDK, `expo-linking`, `react-native-svg`/`reanimated` all have web support), so this was effectively free to try. Known limitation: iOS Safari has never implemented the Vibration API, so the "both" mutual haptic buzz silently no-ops on iPhone browsers specifically (Android Chrome web still gets it) — everything else (orb rendering, presence, invites, deep links via `https://` instead of `mu://`) works the same as native.

- [x] `app/.firebaserc` + `app/firebase.json` hand-written (skipped the interactive `firebase init hosting` wizard since it doesn't script well) — `public: "dist"`, with the critical SPA-fallback rewrite (`{"source": "**", "destination": "/index.html"}`) so a cold visit to an invite link like `/connect/XXXXXX` doesn't 404 before the client router (well, `Linking`'s own parsing) ever runs.
- [x] `npx expo export --platform web` — static export via Metro (project isn't on Expo Router, so this is a single-bundle SPA, not per-route static files), `.env.local` Firebase config correctly inlined at build time.
- [x] **Real bug found in the exported build, on-device-testing lesson applying once again to a third platform (web this time)**: the closed `AddOverlay` sheet hides itself via `transform: translateY(400)` while still being `position: absolute` and full-height — fine on native, where clipping is implicit, but on web a transformed element's *painted* bounds still count toward its scroll container's scrollable overflow even though transform doesn't affect layout size. With nothing upstream clipping it, that extra ~400px bubbled all the way up to `<body>`, making the whole page scrollable when nothing should scroll, which surfaced as a jarring black bar at the top after any browser-triggered auto-scroll (e.g. focusing a text input). Fixed with one line — `overflow: 'hidden'` on the app's root `View` in `App.tsx` — which gives the root a scroll-clipping boundary so off-screen-via-transform content stays invisible instead of leaking into document scroll height. Verified: `document.body.scrollHeight` now stays pinned to the viewport height in every screen state (login/welcome/home, overlay open/closed).
- [x] Smoke-tested the production export locally (`serve dist`) end-to-end: name entry → welcome screen → home (empty state) → invite overlay open/close, no console errors.
- [x] **Deployed**: `firebase deploy --only hosting` → live at **https://mu-app-d2c2e.web.app**. Re-verified against the real deployed URL (not just the local static server) — loads cleanly, no console errors, scroll-height fix holds.
- [ ] Realtime Database security rules (same open item as phase 2 — still "test mode", ~30-day expiry) matters more now that there's a public URL; do this before wide sharing.
- [ ] No responsive/desktop-specific layout pass done — the app renders at its native phone-ish width and leaves whitespace on a wide desktop browser window; acceptable for a link mostly opened on phones, revisit only if that stops being true.
- [x] "(miss u)" subtitle added under the "mu" wordmark on the login screen (`LoginScreen.tsx`).
- [x] **Fixed mobile-browser overscroll bounce revealing the page edge**: swiping on empty space in the live app was triggering the browser's native rubber-band bounce (touch-drag past scroll bounds), briefly revealing a sliver past the app's edge — jarring for a fixed-size app-shell that was never meant to scroll at the document level. Fixed with `overscroll-behavior: none` on `html, body`. This couldn't just be added to `dist/index.html` directly since Expo regenerates that file fresh on every `expo export`; instead created `app/public/index.html` as a project-level override — Expo's web template resolution checks `public/index.html` before falling back to its built-in template (confirmed by reading `@expo/cli`'s `webTemplate.js` source), so this survives every future rebuild.
- [x] Redeployed with both changes — live at https://mu-app-d2c2e.web.app.
- [x] "Oh, and it stands for 'miss u'." appended to the "Why is it called 'mu'?" FAQ answer (`InfoContent.tsx`).
- [x] **Real regression found in the `overflow:'hidden'` fix from the deploy above, and properly root-caused**: after focusing any text input (e.g. the login name field) and navigating on to another screen, the Home screen's header ("mu" + the "•••" menu) would vanish — the whole app looked permanently scrolled up. Root cause: `overflow: 'hidden'` on the app's root View clips content, but per spec it still lets the browser treat that box as a real, if invisible, scroll container — a focused input's native "scroll into view" behavior (the same thing that keeps a text field above a phone's on-screen keyboard) will happily set `scrollTop` on it. Since all three screens (login/welcome/home) render inside that one shared div, a scroll picked up while on login persisted after crossfading to home. First attempt — a `scroll` event listener resetting `scrollTop` back to 0 — did not work and was reverted: `overflow:hidden` containers don't reliably fire `scroll` events for programmatic offset changes in this engine, so the listener never ran. **Actual fix**: swapped to `overflow: 'clip'` (web-only, via a `Platform.OS === 'web'` check — RN's own type doesn't know this value, native keeps plain `'hidden'`) — a CSS value that clips content but, unlike `hidden`, never establishes a scroll container at all, confirmed by testing that `scrollTop` can no longer even be set on the element (stays 0). Re-verified the original login → welcome → home repro end-to-end: header now stays put.

Root cause: nothing told the browser this app's `Text` elements are UI, not a document — so a press-and-hold or an imprecise tap-and-drag on the orb or a name got interpreted as a native text-selection drag (and, on iOS Safari specifically, can trigger the long-press "callout" menu). Verified locally: triple-clicking UI text selects nothing; the name-entry input still selects/edits normally.
